# Party recruitment, public builds and lab challenges

Players open these services from `@adventure`. The party board has 40 advertisements; only the current party leader can publish or refresh one. Each listing has an activity, requested role, beginners-welcome setting and optional 80-character note. Refresh replaces the party's existing listing and starts a new 30-minute expiry. Listings are removed from browsing when the leader logs out, changes character, changes party leadership or the time expires. Temporary registry storage also clears them on map-server restart or script reload. Each dialog selection verifies the listing's revision before displaying details or checking readiness.

The board shows the leader's character name for a voluntary whisper. It neither sends messages nor invites, teleports, reserves an instance or alters progression. The seven supported instance activities call the existing read-only `PN_InstanceMissing` predicate; members already in the advertised party can also use its existing member readiness snapshot. Free hunting/exploration does not claim an instance readiness result.

Build Sharing publishes a chosen existing Build Notebook plus the equipment worn at publication. A confirmation explains that the author name, job, level, note, notebook stats, current equipped items/refines, card/enchant IDs and random-option ID/value/parameter become public. Equipment is labeled separately because a notebook's saved stats can predate the current gear. No account ID, inventory, storage, private lab history or other notebooks are exposed.

Each character has one active numeric share code. Replacing a share invalidates its previous code; unpublishing removes the public author/note/stat/equipment strings. Codes expire after 30 days and expired slots may be reclaimed. A maximum of 256 active snapshots prevents unlimited registry growth; a full board refuses publication. Codes are public lookup identifiers, not passwords. Serial exhaustion at 2,147,483,647 refuses new publication without modifying an existing snapshot.

Snapshots use the existing persistent map-server registry. They are immediately visible on that map server, with persistence governed by rAthena's normal map-registry save schedule. This implementation does not add transactional SQL storage or guarantee the most recent publish/unpublish survives a sudden process crash. Character notebook and lab-best persistence uses the existing character registry and its normal save lifecycle.

The private Damage Lab adds three fixed 60-second targets: a neutral normal training dummy, an armored neutral demon boss and a fire-level-4 demi-human boss. The menu sets all nine target fields explicitly. Players choose a personal DPS goal; a zero goal records ordinary practice. Selecting a challenge from outside the room queues the target and goal for the next lab-console conversation and navigates to the office Damage Lab desk. The console consumes that queue and starts the existing countdown/measurement path after confirmation. These inert targets simulate damage testing, not encounter survival mechanics, and award no items or currency.

Stable-buff completed runs also record up to 12 personal bests separately from the existing three-run history. A best is keyed by exact target, initial buffs and verified server build. A higher DPS run replaces its matching best, including when equipment changes between runs. Different targets/buffs/builds remain separate; if full, a new combination replaces the oldest saved best. Incomplete runs, changed buff states, missing build identity, negative damage and damage values that cannot safely be multiplied by 1,000 are refused. Normal history and its stricter repeat/A-B comparisons remain available.

It checks party ownership/expiry, public consent cancellation and real equipped-item snapshots, share replacement/unpublication/expiry/capacity/serial bounds, fixed target validity, best eligibility/partition/capacity/recreated character reads, and actual Adventure menu routing. Export stubs in the routing-only section verify dispatch; preceding cases run the feature implementations. It requires current Linux map-server objects.
