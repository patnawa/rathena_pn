# Wide economy deployment and migration

The candidate independently implements signed 64-bit wallets, the shared account bank, companion trade/mail/market controls, and retirement of legacy Zeny items. The native protected executable retains its narrow fields: full values and explicit purchase confirmation are shown by PNWallet64. Deploy the compatible DLL and every rebuilt server together; their private inter-server structures have changed.

Do not treat this file as a deployment receipt. Production cutover remains the release operator's step after the combined build, actual isolated protocol sessions, and client tests pass.

3. Create a complete consistent SQL backup and verify its integrity before changing schema or assets. The first widens char/mail wallets and shop values and converts market tables to InnoDB. The other three add replay receipts. 5. With writers still stopped, run `tools/admin/retire_zeny_tokens.py --database <character-database> --output <new-dry-run.json>`. 6. Install all matching binaries and final NPC/data/config changes. Publish the compatible PNWallet64 client release with the existing signed manifest tooling. Select PNWallet64 instead of BankUI in the loader; the two DLLs must not both hook the socket APIs.
7. Start the matched servers and web services. Verify health, no schema/parser/protocol errors, installed hashes, exact financial conservation and migration receipt. Verify no token rows or token listing references remain, and no existing unrelated item stacks changed. Exercise login, bank and market UI with the compatible client before ending maintenance.

## Conversion behavior and failure handling

Item 6024 (17-carat diamond) credits 499,000,000 Zeny per item; 12781 (1M ticket) credits 998,000. Sources are inventory, cart, all seven account storage pages, guild storage (guild leader's account), and mail attachments (current recipient's account). Market listings are references or purchase orders and do not receive a second credit. Their token entries are removed; empty affected shop headers are removed while mixed shops retain other orders.

One InnoDB transaction credits account banks, removes exact owned token rows and market references, and inserts a plan receipt. Overflow, orphan ownership, unsettled token auctions, unknown token-bearing tables, changed plans and failed SQL writes abort. Replaying a committed plan hash returns `already_committed`. New legacy token creation and exchange controls are disabled; the five legacy reward boxes pay their corresponding direct Zeny value after a wallet-capacity check.

No inverse financial migration is provided. Before reopening to players, a failed cutover can restore the verified SQL backup and old binaries/client as one set. After new economic activity starts, do not restore the old database or narrow columns: retain BIGINT and use a compatible forward repair. Never run old map/char binaries together with the new private protocol.

## Staged deployment runner

`tools/admin/deploy_wide_economy.py` accepts a selection JSON with explicit relative `files` and absolute `validation_reports` arrays. `--prepare selection.json --plan new-plan.json --database <name>` records exact live preimages, candidate hashes and passing evidence. `--apply plan.json --expected-sha256 <hash>` verifies all of them again, backs up files, performs ordered graceful shutdown, dumps the character database, restores that dump in an isolated same-image MariaDB container and requires an identical canonical dump, applies schemas, atomically retires tokens and installs matched files. It leaves writers stopped for client publication and controlled startup. Failures do not automatically restore financial data or start mismatched binaries.

The backup/restore helper passed on a real disposable database including an AUTO_INCREMENT gap/high allocator; `/app/pn-muhro-zeny-20260928/deployment-runner-proof/backup-proof.json` contains matching hashes. The graceful shutdown helper passed in a real disposable container with a PID 1 shell, child server process and `restart=always`; it stopped cleanly without an unwanted restart or forced kill. This helper proof does not claim production deployment has happened.
